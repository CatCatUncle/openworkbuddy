## 2026

- **Sep 20** **The boot-failure screen told you to file an issue — even when the gate already knew the fix**. The startup gate checks your Node version and your dependencies and produces a plain-language verdict ("run `npm install`", "re-download from Releases", "get the LTS build from nodejs.org"); but the window only received an error string, and then guessed what to say by matching **English** keywords like `Cannot find module`, `EACCES`, `EADDRINUSE` against it. The verdicts are written in Chinese, so nothing ever matched, and all three fell through to the catch-all: "the server crashed on startup. Paste the line below into a GitHub issue." Measured on all three failure modes (source checkout missing deps, installed build missing files, Node too old) the headline came out word-for-word identical — that one sentence. Somebody who downloaded the app and can't open it was being told, as the only instruction on screen, to open an issue and wait. That is exactly the situation the people in issue #1 were in. The verdict now travels with the error: the gate attaches it as `err.bootProblem`, and the window uses its `fix` directly. Guessing from error text is left for the crashes the gate cannot know about — port already in use, permission denied. The red box now carries only the verdict's headline, not the fix as well: the fix is already spelled out in the body above, and repeating it inside the red box makes it look like part of the error you are supposed to paste somewhere. The `dialog.showErrorBox` path uses the same pair. 370 assertions pass, 0 fail, and 5 mutants are all caught: the advice going back to guessing, the gate no longer attaching the verdict, the red box printing the whole string again, the system dialog missing the wiring, and the window headline going back to guessing.
- **Sep 20** **The startup gate checked dependencies against a hand-written list of three packages** — `express`, `@anthropic-ai/sdk`, `exceljs` — while `package.json` declares 13. I measured what that list actually buys: erasing packages from module resolution one at a time and booting, **only `express` genuinely stops startup**; the other 12 are required after the server is already up. So a miss doesn't crash at the door, it waits until the user reaches for one particular feature, and by then what the error looks like is nobody's problem. Worse, a hand-written list **only ever gets staler**: add a dependency and you have to remember to come back and add it here, and forgetting is completely silent. It now reads `dependencies` from `package.json`, falling back to those three names only if that can't be read (corrupt file, stripped build) — falling back to an empty array would disable the gate outright, which is far worse than a stale list. The wording changed too: printing only the first three made "the whole install failed, all 13 are gone" look identical to "one package is genuinely missing", and those call for different actions. Over three names, it now appends the total. Verified across four cases: a real install passes (exit 0), only `qrcode` missing reads "can't find qrcode", a half install reads "and 12 in total", nothing installed reads "and 13 in total", and the packaged build is told to re-download from Releases rather than to run `npm install`. 133 assertions pass, 0 fail, 4 mutants all caught.
- **Sep 20** **Fetching a web page made the model answer a pointless multiple-choice question every single time**: the tool list carried both `fetch_url` and `render_page`, while in code they are literally the same case — `render_page` *is* `fetch_url` with `render:"force"`. Worse, the prompt had a line teaching it "if you get an empty shell, use render_page", contradicting the `render` parameter's own description: two conflicting instructions for one job. `git log -S` turned up the root cause — a comment written on 2026-09-14 already claimed "merged into fetch_url", but only the words were written; the definition was never deleted, and it sat in the list for another six days. Now it really is gone: 28 → 27 tools, tool table 18294 → 18014 characters. The merged `fetch_url`/`render_page` case in `executeTool` **stays** — live sessions, external MCP clients and historical scheduled tasks may still be holding that name, and falling through to default would get them nothing but "unknown tool". **For external CLI engines (Claude Code / Codex) the trade-off runs the other way**: they don't have this project's `fetch_url`, their own fetch tools don't run JS, and dynamic sites come back as empty shells — there is no choice to be made on their side, so dropping it is a real loss of capability. `render_page` therefore lives on in a bridge-only list (16 tools lent with a browser, including it; 14 without, excluding it). Five mutants all caught: the definition sneaking back into the list, `fetch_url`'s `render` parameter renamed, the name reappearing in the prompt, the bridge copy deleted, and the old-name alias in `executeTool` deleted.
- **Sep 20** **When the settings page asked a provider for its models and got none back, the line of text simply vanished and said nothing.** One moment it read "asking the provider which models it has…", the next it was blank — whatever the answer was, the screen never showed a word of it. Local Ollama suffers most: it answers 200 with an empty list (the service is up, you just haven't `pull`ed anything), which is not an error, so there isn't even a reason to display — and nobody tells you about the one thing you actually need to do, which is `ollama pull` in a terminal. It now says one of three things: a local service with an empty list → which command to run, roughly how big, and that reopening the dropdown after the pull will ask again; a cloud provider with an empty list → plenty of providers simply don't expose this endpoint, the curated list and "type it in" still work; **the request never going out at all** (server down, network gone) → that gets a sentence too, where before it looked exactly like "asked, and there's nothing". The empty result is also **no longer cached client-side** — cache it and you come back from a successful `pull`, reopen the dropdown, and see the same empty list: the hint told you to do something, and doing it changed nothing on screen. Both the chat-model and media-model pickers are fixed (`public/js/app-05.js`), with 5 assertions against the real source and 5 mutants all caught: blanking back to an empty string, caching the empty result again, forgetting to thread `local` through, shouting `ollama pull` at cloud providers too, and the `catch` branch going back to wiping the line.
- **Sep 20** **Connecting a local Ollama gave you no say in which model to use** — the wizard had `qwen3:14b` hard-coded, a ~9GB model a 16GB Mac can't even pull, while the machine already had others installed. The wizard was reading the one model name baked into the provider template, and **what's installed is something only your machine knows**. If Ollama isn't running you aren't left empty-handed: the hint spells out `ollama serve` then `ollama pull`, and leaves an "ask again" link (you go pull a model in a terminal and come back — without it the list stays cached and looks just as empty as before). The model you pick is **actually the one probed**, and it is written to the config only after the probe passes — the old order mutated the config first and probed second, so a failed probe left that change sitting in memory, to be written out by the next save of anything: one failed attempt quietly breaking a setup that worked. The offline fallback also dropped from `qwen3:14b` to `qwen3:8b` (~5GB); 14B is still in the catalog for anyone who wants it. 13 front-end assertions run the real source in `public/js/app-03.js`, and the server half is verified end to end against a fake Ollama: the list comes back, a second call inside 10 minutes is cached (upstream hit exactly once), neither anonymous callers nor ordinary members can reach upstream (this endpoint goes out with the platform's key), "not running" and "malformed address" report differently, the named model really is the one pinged, a failed probe leaves both the on-disk and the in-memory row untouched, and the template path honours the choice too. Four mutants — probe after mutating, template swallowing the choice, fallback back to 14b, owner gate removed — all caught.

- **Sep 20** `gen_diagram` **often delivered the SVG but no PNG** (Feishu docs and Word only accept PNG, so the picture simply didn't go in). Outside the desktop app the conversion shells out to headless Chrome — and the screenshot lands on disk in about two seconds, but the Chrome process can then hang around for another minute without exiting (especially on a Mac with a display attached). - **Sep 20** On macOS the **downloaded app wouldn't open on a double-click**, and at least one person was stuck on 0.6.2 because of it. Nothing is wrong with the build: this project has no $99/year Apple developer certificate, so releases are ad-hoc signed, and anything a browser downloads gets tagged `com.apple.quarantine`. Since macOS 15 the dialog for such an app offers only "Move to Trash" and "Done" — **there is no "Open"** — and the old right-click-to-open trick no longer works either, so most people conclude the software is broken. There's now `curl -fsSL .../install-mac.sh | bash`: a file fetched with curl never carries that tag, so the whole path is dialog-free — detect the chip and pick arm64/x64, download the zip, unpack, move it into Applications, strip quarantine anyway with `xattr -dr`, and re-sign in place if the signature is broken (copying, sync folders and unzip tools all break it, and on Apple Silicon a broken signature reports as "damaged", which tells you nothing about the real cause). It also closes a mutual-clobber: the dev shell from `scripts/make-mac-app.sh` always lands in `~/Applications`, and the installer falls back to that same directory when `/Applications` isn't writable — same name, same place. Overwriting blindly replaces a working install with a shell pointed at a local checkout: your files are still sitting safely in `~/OpenWorkBuddy`, but the app shows zero tasks, which reads as "my data is gone". Each script now recognises the other and stops with instructions instead.
- **Sep 20** The infinite canvas can now **select a group at once**: Shift- or ⌘-click nodes to add and remove, a new marquee toggle in the toolbar lets you drag a box over everything you want, ⌘A selects all, Delete removes them together, Escape backs out. Marquee used to be reachable only by Shift-dragging, but dragging on empty space pans by default — you try it once, conclude it isn't supported, and never try again, so it got a visible switch. The real defect was behind all of that: those keys are bound to the canvas page, but after any mouse click focus stayed on `<body>` — an *ancestor* of the canvas — so keystrokes never passed through it. You could draw the box, you could see the highlight, and then **Delete did nothing, ⌘A did nothing, Escape wouldn't leave marquee mode**, which looks exactly like multi-select was never built. Clicking anywhere on the canvas now takes focus, while clicks on inputs and buttons leave it alone. Two smaller changes: a marquee now selects anything it *touches* rather than only fully-enclosed nodes (dragging a box over half the canvas and selecting nothing is not something anyone will diagnose as a missing half-edge), and a Shift-click on empty space with no drag means "clear the selection". 25 assertions pin it down, including "Delete only deletes characters while you're typing in a field".
- **Sep 20** The drama progress bar **covered the canvas once expanded**. Viewport height was hard-coded as `calc(100vh - 278px)`, and that 278 was measured before the progress bar existed; once it appears — and expanding it grows a blocker list and a shot table on top of that — it pushes the canvas and the chat column below the fold, while the toolbar floating over the canvas at `top: 42px` was measured in that same era and stayed put, landing right on the bar's face so the script and character-shot buttons were permanently hidden. The bar's real height is now measured into `--cp-h` and both the viewport and the toolbar give way; the bar itself is capped (40vh, scrolls past that), because thirty shots make a table taller than the screen.
- **Sep 20** "**N characters have a look-book shot on the canvas that no longer exists on disk**" was often **a false alarm**. Whether a file exists was decided from one workspace listing, and that listing is truncated — 3 levels deep, 500 entries max. Let the workspace fill up, or put assets one level deeper, and every node on the canvas raises that blocker while the files are sitting there perfectly fine. It's two steps now: in the listing means present; not in the listing means ask the disk, one path at a time (capped at 400 per board), because **only the disk gets to pronounce a file dead**. A path that won't resolve counts as "can't say" — better silent than wrongly accusing a file that's still there. One duplicate on the same bar is gone too: the "what's next" line shown when collapsed is the same sentence as the first blocker shown when expanded, and having both up at once reads like two separate failures, so the expanded view keeps only one.
- **Sep 20** "Tidy up · free disk space" is **no longer offered on the empty state**. The first thing someone sees before they've done anything shouldn't be a button urging them to delete things — that's worrying on their behalf about a problem they don't have yet. The feature itself is unchanged; you're still asked about intermediate files when a task finishes.
- **Sep 19** Eval runs **no longer touch your real memory, preferences or quota ledger**, and the task set grew three shapes a single-turn task can't test. The harmful part first: eval used to share one data directory with normal use, so an agent that called `remember` mid-task wrote "the user prefers Firefox" straight into your long-term memory — and the next run was then influenced by what the last one wrote, which makes scores irreproducible and leaves you with memories from nowhere. The data directory is now pointed at `eval/runs/<timestamp>/data/` before anything loads, so a run's entire footprint stays in that one folder. The task set went 15 → 18: a **long-haul task** (12 order files, the spec hidden in one of them, 40+ steps) asks whether a rule read at step 3 still holds at step 30 — the spec has to live in a *file*, because the prompt sits at the head of the history and survives trimming while the tool output in the middle is what gets dropped; a **multi-turn task** runs three turns with the format rule stated once, in turn one, and never repeated; a **memory-recall task** seeds the rules into long-term memory and mentions none of them in the prompt, plus two deliberately irrelevant seeds, to see whether it forces unrelated memories into the deliverable. Alongside it, a **free offline gate** (`node test/eval.js`, 100 assertions, zero model calls): feed every task's checks an empty directory and require that **not one of them goes green** — an agent that did nothing scores zero, so any check still passing there isn't grading, it's giving marks away. The gate caught two such freebies in existing tasks on day one: a pure negative assertion that passed when the model crashed without output, and a "local copies cleaned up" check that passed when the model simply deleted both source files. Finally, "changed a prompt or a tool description? run the eval" is now written into CONTRIBUTING, with the triggers spelled out (the agent.js system prompt, tool `description` text, skill prompts, trimming and memory-injection logic).
- **Sep 19** When two tasks change the same repo, **the later one gets its own git worktree** (`worktree.js`). The old isolation was one output folder per conversation — fine for document work, useless the moment the working directory is your own code repo: both tasks read the same `src/`, A changes a function to three arguments, B is still holding the two-argument text, and B's write erases A's change. Nothing errors, the tests may even stay green; what's broken is the version in between. The approach is Codex's: same `.git`, separate working copy, changes land on `owb/<session>`. Three deliberate limits: **only a collision triggers it** (one person with one task is the overwhelming majority, and dropping someone into an unfamiliar directory for no reason just means they can't find their files); **the first task is left alone** (it edits the tree in front of you, which is what you expect — the later one is the extra); and it **never merges back**. A few more things that would make the feature a lie if skipped: your uncommitted changes are **carried over** (not the `.gitignore`d ones, or an 800MB `build/` would ride along), because without them the second task sees a repo rolled back to the last commit and redoes work you already did; the work is **auto-committed** to that branch at the end, since uncommitted changes can't be merged and you'd follow the hint, run `git merge`, and find the branch identical to your own; a run that produced nothing is **removed on the spot**, directory and branch, or every collision would leave behind a branch nobody dares delete; and anything with work in it is **never deleted** — after 14 days only the directory goes, the branch stays. The collision list includes terminal runs (one web task plus one terminal task is the common case, and they're separate processes that see each other only through the `data/cli-live` ledger). The prompt states outright that the agent must not merge, rebase or push. Every failure mode (no git, no first commit yet, bare repo, patch won't apply…) falls back to the old behaviour in the original working directory with one log line, so a task never fails to start because of this. `openworkbuddy worktree` lists them; `openworkbuddy worktree 清理` sweeps the empty ones
- **Sep 19** A **super-admin** tier, and permissions rebuilt as RBAC. **any admin could demote, disable, delete or reset the password of any other admin**, and mint new admins at will. Two people disagree and whoever clicks first wins; that isn't a permission model, it's first-mover advantage. Worse in branch orgs: the protected `owner` flag was only ever set for the **first account on the whole install**, so orgs created later had nobody protected at all. There are now four tiers — super admin / admin / auditor (the tier already existed, it just wasn't ranked: can open the console and see the whole org's usage and billing, changes nothing) / member — and only two rules: **you can only manage a strictly lower tier** (equals can't touch each other), and **granting a role requires outranking both the person and the role** (so an admin can promote someone to auditor but can never produce a second admin). There are four routes to minting an admin — change role, create account, issue an invite code, department template — and all four now go through the same check; leaving one open makes the rule one step away from meaningless. Each org has exactly one super admin and the seat can only be **transferred, never issued**: two super admins would reopen rule 1 at the top tier — either they can depose each other (first-mover advantage is back) or neither can (one mis-click is permanent). Two escape hatches so nobody gets locked out: the platform super admin (the default org's) can reassign across orgs, and if they're the one who's gone, `openworkbuddy owner <username>` on the server itself — same reasoning as `passwd`: anyone who can read `users.json` already owns the machine. **Neither is ever exposed over HTTP.** Upgrades migrate once: the legacy `owner` boolean becomes a role, and orgs that never had one get the earliest active admin. The whole thing lives in one `rbac.js` you can read in a single screen — nobody trusts a permission model they can't finish reading. The role dropdowns in the console are drawn from what you can actually grant — an admin no longer sees "admin" in the list, because a visible button shouldn't be one that only tells you no after you press it; and when editing someone, their current tier is shown first even if you can't change it, so the dropdown never defaults to "member" and makes a demotion look like the status quo. 103 new assertions, each "must refuse" paired with a "must allow".
- **Sep 19** Storyboard shots can now be **rolled back to an earlier version**. Change one line of dialogue, re-run, and the previous first frame was overwritten by a file of the same name — gone. Recording the path doesn't help: the path is unchanged, it's the bytes underneath that were replaced. So snapshots store **the bytes**: first frame, last frame, video and voice go into a sha256-addressed object store, identical content stored once (re-run ten times, roll back ten times, and most of the intermediate states are duplicates). "Versions" on any shot lists what it has looked like, thumbnails read straight from the snapshots, and restoring swaps **the whole shot** back to that version rather than merging — merging leaves you last version's video against this version's first frame, which looks exactly like success on screen. The current version is snapshotted before a restore, so a wrong rollback is itself reversible. A version that has been swept is genuinely gone: the button is simply disabled and says which kind of gone, rather than being a button that does nothing. The ledger lives in the workspace where the model can write to it, so no path from it is ever trusted — everything resolves back under the root and is re-checked; anything outside is refused.
- **Sep 19** A channel in arrears is **cut off after one hit**, not retried daily. Alibaba's Model Studio reports arrears as **HTTP 400** with no "balance", "quota" or "overdue" anywhere in the body — just `Access denied, please make sure your account is in good standing` and `code: Arrearage`. 400 isn't in the hard-error set and the breaker's wording list caught none of those, so arrears read as "unlucky this time": the next call went out, waited out another timeout, and did the same every day until someone topped up. The factory **default video model** hangs off that channel, so video generation was walking into a wall that was never going to move. `Arrearage` and that `in good standing` sentence are now recognised, one hit trips it, and the message says the channel is out of credit and points at Settings → Models instead of "retrying in a few minutes" — no amount of waiting fixes a wrong direction. - **Sep 17** Every API the company buys now goes through one door, and neither staff nor other programs touch the real keys any more. Each key carries its own capability switches: an image-only key that calls speech gets a 401 on the spot, and `/v1/models` does not even list the chat models for it — every id in that list is a promise that you may call it, and a promise that answers 401 sends the developer on the other side digging through their own code before they find the switch. - **Sep 17** The relay bills the way each vendor actually sells, and the quota is a gate rather than a report. - **Sep 17** Source files in the workspace now render as code: a line-number gutter that stays put when you scroll sideways, five-colour highlighting, and — the part that mattered — **no wrapping**. They used to fall through to the plain-text `<pre>`, which is tuned for logs and prose: `white-space: pre-wrap` plus `overflow-wrap: anywhere` keeps a long URL from stretching the panel, but the same rule applied to code breaks words at *arbitrary* points — `fun` on one line, `ction` on the next. That is what "looks like mojibake" meant: every character correct, every break wrong. Bundler output is worse still — a rolldown/esbuild `.mjs` is routinely one line of fifty thousand characters. So when a file looks minified (longest line over 400 characters) it is laid out for you by default: broken at `{` `}` `;`, indented by bracket depth, with a banner naming the longest line's length and a "show original" toggle beside it. The reformat only inserts newlines and indentation — not one character changes, and nothing is written back to the file. It **deliberately does not build an AST**: bundler output contains every strange construct there is, and a parser that meets one gives up on the whole file, whereas a scanner that only understands strings, comments and regexes can at worst break lines in ugly places without ever losing content. Those three it must understand — the braces in `var q="}}}"` are not structure, the slashes in `/[/{};]+/g` are not a comment, the semicolons in `for(let i=0;i<3;i++)` are not statement ends — and each has its own test. Highlighting covers six language families (C-like / `#`-comment / JSON / CSS / tag markup / SQL), with colours measured against the dark `#16181f` background (comments went from 3.1 to 5.2 contrast — a comment is there to be read, not to hide). Past 5,000 lines only the first 5,000 are drawn, and the banner says so (the file itself is untouched; download it and it is complete)

- **Sep 17** Skills get screened before they're installed. A skill's body *is* a set of instructions aimed at the agent, and the agent has a shell — install one from a link and it will be followed on the next task. So everything is scanned first: a directory, a single `.md` from GitHub, or text you pasted into the box yourself — all three go through the same gate. Three verdicts: **clean** installs; **worth a look** (outbound hosts, dependency installs, reading environment variables) shows you the actual lines and asks once more; **don't** (`curl | bash`, reading `id_rsa`, rifling `~/.aws`, `rm -rf ~`, reverse shells — 10 rules in all) is blocked, and only a platform admin can override, which is written to the log *and* to `.install.json` inside the skill folder: which repo, which commit, who waved it through, what the scan said. No score: of 34 rules only 10 can block and the other 24 only ever warn, because nobody can answer "it scored 7.5, do I install it?". It reads combinations, not keywords — `printenv` on its own means little; `printenv` next to an outbound address means something — and a line preceded by "don't" / "never" is ignored, since "never use `curl | bash`" is security advice, not an attack. - **Sep 17** Skill and connector screening can borrow a second ruler from outside: with [toolward](https://github.com/CatCatUncle/toolward) installed on the machine (another project by the same author — 37 rules in six families: prompt injection and tool poisoning TW1xx, supply chain TW2xx, secrets TW3xx, execution and permissions TW4xx, network and exfiltration TW5xx, governance TW6xx), installing a skill or saving a connector runs a second pass, and both sets of findings land in one list with each line labelled by who said it. `.install.json`, the override record and the explanation text did not change by a single character, because the external report is shaped **exactly like** the built-in scanner's: the gate, the explanation and the on-disk record needed no edits at all — only a `merge()` at each of the three install entry points. The whole thing has an `OPENWORKBUDDY_TOOLWARD=off / advisory / auto` switch (the environment variable wins over the setting), and the test suite turns it off by default: otherwise a machine with toolward installed globally would quietly change skill-guard's own 76 assertions, and green would depend on what the developer happened to have installed
