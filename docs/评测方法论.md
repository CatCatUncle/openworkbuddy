# 评测方法论 — 为什么这么设计（v3）

> 背景：v2 时代 12 道题连续多轮 12/12 全过 100%，成绩单失去了区分度——这不是智能体满分，
> 是**考卷太简单**（天花板效应）。v3 参照业界智能体评测的通行做法重造，本文记录依据，防止日后改回去。

## 一、三条独立的评分线

| 线 | 回答什么问题 | 怎么算 |
|---|---|---|
| 机器判分 | 硬性对错：产物在不在、数字对不对 | 确定性 checks（跑代码、对数字、验结构），只认硬证据 |
| 稳定性 | 稳不稳：同一题重复 k 次表现一致吗 | pass@1 均值（能不能）+ k 次全过题数（每次都行） |
| AI 评委 | 质量：机器测不了的「做得好不好」 | 逐条质量维度二元判定（true/false），分数 = 达标占比 |

三条线互不污染：评委打分再高也救不了机器判挂的硬伤；机器全过但评委指出「没自测」「硬编码」照样暴露。

## 二、为什么每题要重复跑（--repeat k）

智能体是随机系统，跑一次说明不了任何事。业界通行两个互补口径：

- **pass@k**（k 次里至少 1 次过）：衡量「能力上限」，能不能做出来。
- **pass^k**（k 次全过，τ-bench 提出）：衡量「可靠性」，交给用户敢不敢。数学上 pass^k = p^k，
  单次 90% 的智能体连续 5 次全对只有 59%——这就是「演示能跑」和「产品能用」的差距。

Terminal-Bench 等基准默认每题跑 3 次。本项目 UI 提供 1/3/5 三档，3 次是性价比推荐档。
时过时不过的题标 ⚡ flaky——它们是最值得修的：说明能力有了但不稳，通常是提示词或工具契约的问题。

## 三、确定性失败码（failure taxonomy）

「挂了」不是诊断。每个失败的尝试按**越硬的死因越优先**归成唯一一类：

`crash（崩溃）> timeout（超时）> max_steps（步数用尽）> loop_suspect（同一工具同参数连调≥3 次）
> tool_error_storm（工具报错≥5 次）> missing_artifact（没交产物）> wrong_output（内容不对）`

聚合后一眼看出这轮败在哪一类，对着类修，不用逐题翻日志。思路来自 MAST（多智能体失败模式分类）：
失败要能归因才有改进方向。

## 四、AI 评委为什么改成二元判定

v2 让评委按 rubric 打 1-5 分，业界已知三个坑：

1. **尺度漂移**：每个评委模型心里的「3 分」不一样，跨轮不可比。
2. **长度偏置**：LLM 评委系统性偏爱长回复（对人类评分高估约 17 个百分点），写得啰嗦反而得高分。
3. **不可复现**：同一份产物两次打分能差 1-2 分。

v3 把每题 rubric 改写成 2-4 条**具体的质量问题**（如「是否真的自己运行验证过」「改动是否克制」），
评委逐条只答 true/false，拿不准一律 false。二元判定一致性远高于打分，且每个 ✗ 直接就是改进项。
评委只判每题首轮（成本减 k 倍，且首轮是无偏样本）。

## 五、基线钉扎与回归点名

评测的头号用途不是「考多少分」而是**「这次改动有没有把什么改坏」**（Anthropic：能力评测 vs 回归评测）。

- `--save-baseline` 或界面「📌 设为基线」把某轮各题通过率钉进 `eval/baseline.json`（随仓库提交）。
- 之后每轮自动逐题算 Δ，退步的题**点名**（不是只给总分）：总分不变但 A 题修好 B 题改坏，必须暴露。
- 每轮成绩盖 commit，历史表能横向对比任意两个版本。

## 六、出题原则

- **分层**：L1 基础（单步就能对）/ L2 进阶（有陷阱：带引号 CSV、格式服从、大海捞针）/ L3 高难
  （多约束交付：跨文件重构去重、两表关联缺数处理、日志管线三件套跨产物一致性）。天花板了就加层，不改旧题。
- **查结果状态，不查过程步骤**（Anthropic）：只验产物（文件在不在、数字对不对、跑起来对不对），
  不规定「必须先做 X 再做 Y」——智能体用聪明办法绕路到达也算对。
- **陷阱要真实**：缺价格的品类、含逗号的引号字段、四种日期写法——都是真实工作里会遇到的脏数据。
- **题目会饱和**：连续多轮全过的题失去信息量，该加新题或加难，别删旧题（保留回归保护）。
  SWE-bench 的教训：题目泄漏进训练数据后成绩虚高，固定题库要定期审视。
