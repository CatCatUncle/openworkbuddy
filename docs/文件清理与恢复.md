# 文件清理与恢复

此页对应 v0.18.3 的可恢复文件回收逻辑。

## 哪些入口会回收

“成果文件 → 整理文件夹”、任务结束后的中间文件清理卡，以及资料库的文件和空文件夹删除、本地产物/工作区文件删除，统一使用可恢复回收。

- 桌面版使用系统废纸篓或回收站。系统拒绝回收时报告失败，不回退到永久删除。
- 纯服务端运行时，将文件或目录整体移入原工作目录/资料库根的 `.trash/files/<编号>/item`，同时写入 `restore.json`。移动失败不回退到直接删除。
- 回收之前、以及每一项移动之前检查运行中的任务、CLI 与后台命令；目录仍在使用时拒绝操作。不能把清理当作停止任务的方法。
- 不再仅凭 `out`、`dist`、`build`、`target` 这些通用目录名认定整目录是缓存。依赖和缓存候选默认不勾选，仍需用户核对清单。
- “已回收多少”表示移出了原位置，清空回收区之前仍占用磁盘空间。部分失败分别报告成功与未确认的项。

新界面会先确认服务支持可恢复回收。若连接的仍是旧服务，会提示更新并重启，拒绝发送删除请求。服务端代码更新需重启后生效；请在当前任务结束后更新，避免打断正在渲染的工作。

## 怎样恢复

桌面版：打开系统废纸篓/回收站，找到原文件名或目录名，使用“放回原处”或“还原”。清空系统回收站后的恢复不由应用保证。

服务端：在对应工作区或资料库根目录打开 `.trash/files`。每个编号目录的 `restore.json` 记录 `original`（原始完整路径）、`name`（原文件名）、`at`（回收时间）及 `payload`（保存内容的名称）。`item` 保存原始字节；若原件是文件夹，`item` 也是完整文件夹。

恢复时按记录将 `item` 移回原路径并恢复原名。若原位置已经有重新生成或修改过的文件，先恢复到另一个目录进行核对，保留两份，避免覆盖新成果。点开头的目录可能在文件管理器中隐藏，可通过地址栏或“前往文件夹”输入路径进入。

回收记录属于所在目录，不会进入资料库搜索、成果列表或下一轮清理候选。应用不会因为回收成功就自动清空它。

## 修复前已经删除的文件

v0.18.2 及更早版本的“清理中间文件”会直接删除文件，不会补出废纸篓副本。本次修改不能追溯恢复那些文件；需要检查已有备份、源素材或重新生成的结果。

以上保证适用于列出的应用界面入口。Agent 通过终端执行的 `rm`、Python 文件删除或第三方程序自己的清理，并不会被操作系统自动变成废纸篓操作。应用缓存、日志与账号数据的维护策略也与用户文件回收分开管理。
