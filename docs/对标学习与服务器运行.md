# 对标学习与服务器运行

## 从 Mosoo / Multica 借鉴了什么

这两个项目的定位不同，但有四个值得吸收的共同点：

1. **一次执行有稳定身份**：任务、运行、事件、文件和后续追问不能散落在多处。OpenWorkBuddy 已有会话、成果子目录和本地 Trace，后续继续把它们用同一个 run/trace 关联起来。
2. **过程必须可观察**：工具调用、模型、耗时、失败原因、Token 和产物都能回放。Trace 页面按工具/模型分开显示，并保留原始输入输出。
3. **失败要能恢复**：重试、超时、取消、继续执行和版本快照应该是运行时能力，而不是靠用户重新描述。短剧画布下一阶段会把节点指纹、脏状态和下游重算接上。
4. **运行时与产品解耦**：桌面端可以跑本机 CLI，服务器可以跑容器/PM2；模型和 Agent 引擎通过配置切换，不把用户锁死在一个供应商。

OpenWorkBuddy 不直接复制它们的技术栈：当前项目坚持零前端构建、JavaScript 本地优先、文件交付和 Markdown Skill 扩展。这样更适合个人电脑、本地素材和希望读懂 Agent 主循环的贡献者。

## 能不能部署到服务器长期运行

可以。推荐服务器使用 Docker Compose：

```bash
git clone https://github.com/CatCatUncle/openworkbuddy.git
cd openworkbuddy
bash deploy.sh --domain buddy.example.com
```

它会使用 `restart: unless-stopped`，数据持久化在 `wb-data`，健康检查访问 `/api/auth/state`，前面由 Caddy 负责 HTTPS。没有域名时也可以只绑定 `127.0.0.1`，再交给现有 Nginx 反代。也可以使用 PM2：

```bash
HOST=127.0.0.1 PORT=3800 OPENWORKBUDDY_HOME=/srv/openworkbuddy-data \
  pm2 start server.js --name openworkbuddy
pm2 save
```

服务器部署前必须关闭开放注册、创建管理员、启用安全中心的命令审批，并为数据目录做备份。不要把 3800 端口裸露到公网；Agent 具备文件和命令工具，公网部署必须有 HTTPS、登录和权限控制。

## Chrome CDP 的边界

`chrome_cdp` 是可选工具，只连接 Agent 所在机器的 `127.0.0.1`、`localhost` 或 `::1`，默认端口 9222。它支持列出标签页、读取页面、打开 URL、点击、输入、执行页面脚本和截图。

在需要它的机器上，单独启动一个用于自动化的 Chrome 配置目录：

```bash
google-chrome --remote-debugging-port=9222 --user-data-dir=/tmp/openworkbuddy-chrome
```

macOS 可使用：

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 --user-data-dir=/tmp/openworkbuddy-chrome
```

服务器上的 OpenWorkBuddy 只能控制服务器上的 Chrome，不能穿透网络控制你个人电脑的 Chrome。不要把 CDP 端口通过公网、端口转发或反向代理暴露出去；如果以后需要远程浏览器，应单独做带身份认证、短时授权和审计的 Browser Worker。
