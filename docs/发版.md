# 发版

一句话版本：**先改 `package.json` 的 `version`，再打同名 tag，推上去就完事**。

之前这份清单只存在于 `.github/workflows/release.yml` 第一行的注释里，而那行恰好漏了最关键的第一步。

## 步骤

```bash
# 1. 改版本号。它有两个下游：安装包的文件名，和「检查更新」的判断基准
#    （updater.js 的 currentVersion() 读的就是 package.json）
#    忘了改会怎样：Release v0.1.7 里挂的是 OpenWorkBuddy-0.1.6-mac-arm64.dmg，
#    而且每一个刚装上最新版的用户，「设置 → 关于 → 检查更新」都会永远告诉他有新版。
vim package.json        # "version": "0.1.7"

# 2. 依赖动过的话，同步 NOTICE.md 里那份第三方署名总账（e2e 里有闸门会卡，
#    漏了 npm test 就红，不用靠记）

# 3. 本地跑一遍全套（约 2 分钟）。流水线也会跑，但本地先过一遍省一次 CI 往返
npm test

# 4. 提交版本号改动，打 tag，推
git add package.json && git commit -m "v0.1.7"
git push origin main
git tag v0.1.7 && git push origin v0.1.7
```

推完 tag 之后流水线会自己跑（`.github/workflows/release.yml`）：

1. **test**（macOS）：先核对 `package.json` 的版本号和 tag 一致——**对不上会当场红，不会打出一个错号的包**——然后跑 `npm test`。
2. **build**（macOS + Windows 两条腿并行）：`fail-fast: false`，一条挂了另一条照样打完上传。
3. **release**：把两边的产物合到一起建 GitHub Release。

## 产物

| 文件 | 给谁 |
|---|---|
| `OpenWorkBuddy-*-mac-arm64.dmg` / `.zip` | Apple 芯片 Mac |
| `OpenWorkBuddy-*-mac-x64.dmg` / `.zip` | Intel Mac |
| `OpenWorkBuddy-*-win-setup.exe` | Windows 绝大多数人（一个包同时支持 x64 / ARM，装时自动选） |
| `OpenWorkBuddy-*-win-x64-portable.exe` | Windows 免安装版（公司电脑不让装软件时） |
| `OpenWorkBuddy-*-win-arm64-portable.exe` | 同上，ARM 机器 |

没有 Linux 安装包。Linux 上跑源码（`install.sh` 支持）或用 Docker（`deploy/`）。

## 出了状况怎么办

**Windows 那条腿红了，Mac 的包还想发**——已经是默认行为：`release` job 的 `if` 里有 `!cancelled()`，
单平台失败不会拦住建 Release。但这种情况下 Release 会**落成草稿**（`draft: true`），
因为正文里写死了 Windows 的文件名，缺了它直接发出去等于给用户指几个不存在的下载链接。
去 Release 页面把正文改了再手动发布，或者修好重打 tag。

**测试没过**——`build` 整个被跳过，`release` 也不会建空 Release。修完重新 `git tag -f` 不如直接换个新号：
tag 已经推过的话，用 `git push origin :v0.1.7` 删远端再重打，但已经发出去的 Release 要手动删。
更省事的做法是版本号往前走一格。

**想验证流水线本身通不通，又不想发版**——Actions 页面手动触发 `release` workflow
（`workflow_dispatch`）。它会打包但不建 Release，版本号一致性那条也会自动跳过。

## 发版之外的日常红绿灯

`.github/workflows/test.yml` 管 PR 和 main：ubuntu 上跑不需要屏幕的 15 个套件（几十秒回结果），
macOS 上跑全套（含 e2e，要开真 electron 窗口和验 `.app` 装机态）。两条腿都是硬闸门。
