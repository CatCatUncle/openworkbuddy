# OpenWorkBuddy 架构优化路线（2026-08）

> 写给未来的自己和贡献者：这份文档回答三个问题——现在的架构长什么样、哪里会先撑不住、按什么顺序改。
> 每一项都带「为什么 / 怎么做 / 怎么算做完」，验收一律以 `npm run eval` 跑分不回归为底线。

## 一、现状盘点（as-is）

一句话：**单进程 Electron 应用，里面住着一个 Express 服务和一个手写的 agent 循环，前端是一个无构建的单文件页面。**

```
Electron main 进程
├── server.js        Express :3800（会话/设置/评测/技能/记忆 全部 API）
├── agent.js         agent 主循环（步循环 + 自动续跑外循环 + 子代理递归）
├── tools.js         ~20 个内置工具 + 写后自检（JS/JSON/MD/HTML/PY/SH）
├── llm.js           多模型适配（DeepSeek / OpenAI 兼容 / …）
├── memory.js        长期记忆（JSON 文件 + 关键词召回）
├── diagram.js       四类图渲染管线（echarts SSR / viz WASM / mermaid / plantuml）
├── feishu-doc.js    飞书 convert API 写文档
├── eval/            评测 v2（12 题黑盒 + 机器判分 + AI 评委 + 人工打分）
└── public/index.html  单文件前端（~310k 字符，一个内联 <script>）
```

这套架构的**刻意选择**要先说清楚，免得后人当成债来还：

- **无构建**：`index.html` 直接改直接刷新，没有 webpack/vite。这是特性不是欠账——贡献门槛为零。
- **JSON 文件当数据库**：sessions/users/memory 全是文件。单用户桌面场景下够用且可 `cat` 可 `git diff`。
- **server 跑在 Electron main 里**：让 mermaid/截图白嫖 Electron 的隐藏窗口，代价是重业务会卡主进程（见 P2）。

## 二、真实的痛点排序

按「先撑不住的先修」排，不按「听起来高级」排：

| # | 痛点 | 证据 |
|---|------|------|
| 1 | **上下文管理粗糙**：长任务靠「裁剪最老消息」保命，裁掉的可能正是关键约束 | 自动续跑上线后，20 轮长任务会把早期决策全裁飞 |
| 2 | **记忆召回是关键词匹配**：换个说法就召回不到 | memory.js 现状 |
| 3 | **改提示词/工具全凭手感**：eval v2 刚补上「有没有退步」的答案，但还没进工作流 | 本轮之前 11 题只有机器判分 |
| 4 | **单文件前端逼近可维护边界**：310k 字符一个 script，改评测页要先定位 splice 区间 | 本轮改 UI 的实际体感 |
| 5 | **run_shell 无沙箱**：agent 写错一条 rm 就是真删 | tools.js 现状 |
| 6 | **重任务卡主进程**：评测已用子进程隔离，但 agent 本体还在 main 里 | eval/run.js 已 spawn |

## 三、路线图

### P0 · 本轮已落地（2026-08）

- ✅ 长任务自动续跑：`auto_continue_rounds` + PROGRESS.md 断点纪律（agent.js 外层 `for(;;)`）
- ✅ 评测 v2：整 agent 黑盒 12 题、三条评分线、commit 盖章可对比版本
- ✅ 写后自检扩到 Python（ast.parse）/ Shell（bash -n）
- ✅ gen_diagram 四类图离线渲染 + 飞书文档原生表格/插图
- ✅ 主动记忆：系统提示词要求收尾前把「下个月还成立的事实」remember 掉

### P1 · 上下文工程（预计 1-2 周，收益最大）

**为什么**：自动续跑把任务时长拉到了小时级，「裁最老的」策略在长任务里必然丢关键信息。这是当前对结果质量影响最大的单点。

**怎么做**（按顺序，每步独立可交付）：
1. **工具结果分级压缩**：tool_result 进 history 前按工具分类——`read_file`/`fetch_url` 这类「可重取」的结果在超过 N 步后压成一行摘要+路径（要用再读一次），`run_node` 报错这类「不可重现」的保留全文。
2. **裁剪时生成「被裁摘要」**：现在裁剪是静默丢弃；改为把被裁的消息批量让模型压成一段「前情提要」插回 history 头部（一次裁剪一次小模型调用，成本可控）。
3. **PROGRESS.md 从纪律升级为机制**：续跑轮开始时由框架自动把 PROGRESS.md 内容注入 system 而不是指望模型自己去读。

**怎么算做完**：造一道 40 步以上的长任务 eval 题（中途埋一个「第 3 步说过的约束」），裁剪后仍能守住约束即通过。

### P2 · 评测驱动开发闭环（与 P1 并行，流程改动为主）

**为什么**：eval v2 的能力已经齐了，缺的是「改核心代码必跑」的习惯和基线管理。

**怎么做**：
1. 仓库存一份 `eval/baseline.json`（某 commit 的机器分+评委分），`npm run eval` 结束自动 diff 基线并高亮回归项。
2. 提示词/工具描述改动 = 必跑 eval 的触发条件，写进 CONTRIBUTING。
3. 题库补短板：长任务题（P1 验收题）、多轮对话题、记忆召回题。

**怎么算做完**：连续三次核心改动都有 eval 前后分数记录在 commit message 里。

### P3 · 记忆向量召回（1 周）✅ 2026-08-24 完成

落地形态与原计划略有出入，记录如下：
- llm.js `createEmbedder(config)`：优先 `config.embedding` 显式指定；否则在模型列表里找**认识的**厂商复用 key（DashScope/智谱/OpenAI/本地 Ollama；DeepSeek/OpenRouter 没有 embeddings 接口，不猜）。没 key 的条目跳过（Ollama 例外）。连挂 3 次自行停用并留痕，绝不静默。
- memory.js：向量单独存 `data/memory_vectors.json`（memories.json 保持人能读；换嵌入模型自动全量重算）；`ensureVectors()` 启动/换模型/新记一条后后台补算。
- **召回只在装不下时发生**：promptBlock 超 6000 字预算才筛，打分 = 0.7×余弦 + 0.3×中文二元组关键词；没向量退关键词，没线索退新旧排序（老实现的盲切尾巴恰好吃掉最新记的，已修）。挑没挑、挑了几条，提示词里明说。
- 线索（hint）= 用户最后一条消息前 500 字；专家拿委派任务描述当线索。提示词组装链因此转 async。

**为什么**：关键词召回对中文尤其脆（「部署」召不回「上线」）。

**怎么做**：不引入向量库——单用户几百条记忆，**本地 embedding + 余弦暴力扫**就是最优解：
1. llm.js 加 embed 接口（DeepSeek/OpenAI 兼容的 embeddings endpoint）。
2. remember 时算一次向量存进 memory JSON；召回时对 query 算向量、内存里全量余弦排序，取 top-k 再过一遍现有关键词逻辑兜底。
3. 没配 embedding 模型时静默退回纯关键词（不新增必填配置）。

**怎么算做完**：记忆召回 eval 题——换措辞提问能召回原记忆。

### P4 · 前端解体 ✅ 2026-08-25

**为什么**：单文件是特性，但 277k 字符的**单 script** 不是。可以既无构建又分文件。

**实际做法（与原计划的偏差）**：没用 ES Modules，用的是**顺序加载的经典脚本**（`public/js/app-01.js` ~ `app-06.js`，六个 `<script src>` 按序排列）：

- 经典脚本共享同一个全局作用域（含顶层 let/const），六段拼回去和原内联块**逐字节相等**——语义等价有数学保证，不需要梳理 import/export 依赖图。ESM 方案要先把 283 个顶层声明的引用关系全理清，改动面和风险大一个量级，收益却一样（文件变小、刷新即生效不变）。
- 切分点由 acorn 按**顶层语句边界**贪心切（单片 ≤55k 字符），每片独立过 `node --check`。
- 经典脚本拆分唯一的语义风险是「立即执行的顶层代码前向引用了后面片段的声明」（函数提升不跨 script 标签）——自动审计过一遍，**零前向引用**。
- 拆分/审计脚本在会话 scratchpad 的 split.js，需要重切时可复跑。

**验收**：单片最大 54,788 字符（目标 ≤60k）✅；index.html 缩到 75k ✅；浏览器全页面回归（登录/新任务/专家/自动化/任务历史/设置，刷新后控制台零报错）✅；改代码直接改 `js/` 下分片、刷新即生效，开发体验不变 ✅。

### P5 · agent 执行隔离与安全（择机）— 软护栏 ✅ 2026-08-24；utilityProcess 明确缓做

- run_shell 软护栏 ✅：动手前盘点发现安全中心的 checkCommand + 界面审批流早已覆盖 `rm -rf`（删除保护）、sudo/mkfs（询问名单）和文件黑名单，真正缺的是路线图点名的那几个形态。已补一张 `DANGER_PATTERNS` 高危表：`> /dev/` 直写、`dd of=/dev/`、`compose down -v`、`git push --force`、SQL 删库/清表、格盘分区。**全档位生效（全自动也拦）、永久放行名单盖不住**、批过一次按 danger:key 记在本会话不反复骚扰、「只看不动」档仍是直接拒绝。
- agent 循环挪 `utilityProcess`：**缓做，有意为之**。mermaid 渲染（gen_diagram/browser-render）依赖 main 进程的 BrowserWindow，挪出去要么断这条能力要么加一条 IPC 往返桥；eval 已在子进程跑通证明可行性，但眼下收益（崩溃隔离）对单用户桌面场景不及改造成本。等出现真实的「agent 干崩 main」案例再动。

### 追加 · 长跑韧性三连 ✅ 2026-08-25

自动续跑把任务拉到小时级后，三个新的「先撑不住」浮出来，一并补上：

1. **卡循环检测（agent.js）**：同一工具+同一入参连续拿到**同一结果** 3 次 → 注入系统提醒换思路；5 次 → 直接拦截不执行（返回错误结果说明为什么）。键里带结果指纹，「改一遍读一遍」的正常校验循环不会误伤——文件变了内容就变，计数自动清零。另有工具级连败计数（换参数也算）连挂 4 次提醒一次。此前只有提示词纪律（"连续失败 3 次就换思路"），现在是机制。
2. **token 预算护栏（设置 → Agent）**：`max_tokens_budget`，整棵任务树（含专家、含自动续跑）共享一个用量闸，80% 预警、超了强制收尾且**不再自动续跑**（预算是花费上限，续跑就违背本意）。0 = 不限（默认）。步数挡不住小步快跑烧钱，时间挡不住便宜模型慢慢磨，这道闸按钱的正比例量收口。
3. **重启中断标记（server.js）**：正在跑的会话 id 落盘 `data/running.json`（起跑写入、收尾清除）；启动时清算名单，被打断的那轮在回放里补一条明确的中断说明（进度都在，可以说「接着上次进度继续」）。此前应用中途重启，那一轮就无声断在半空，用户分不清是完成了还是死了。

验收：零 token 假模型压测（循环 4 执行 3 拦截 1 提醒；预算 80% 预警→超限收尾→零续跑）+ 真实重启清算实测 + `npm test` 全绿。

### 明确不做的事

- ❌ 微服务 / k8s / 独立数据库——单用户桌面应用，永远不需要。
- ❌ 引入前端框架和构建链——无构建是产品性格。
- ❌ 向量数据库服务——几百条记忆用暴力扫。
- ❌ 多租户——这是个人 agent，不是 SaaS。

## 四、执行节奏

P1 → P2 是主线（质量闭环），P3 插空做（改动面小），P4 在下一次「改前端改到烦」时启动，P5 看 utilityProcess 的实际收益再定。每个 P 完成后跑全量 eval 记基线，成绩写进 commit。—— 2026-08-25 记：P1~P5 全部收官（P5 的 utilityProcess 一项为有意缓做，理由见上）。
