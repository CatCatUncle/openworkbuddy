# 远程访问：在手机和别的电脑上用

OpenWorkBuddy 默认只听本机（`127.0.0.1`）。想在手机上、或者在另一台电脑上用，
得先决定「让谁能连到它」——这一篇就讲这件事，以及每种做法各自把什么暴露出去了。

先说结论，按「够用且最不冒险」排：

| 做法 | 谁能连 | 要不要动路由器 | 适合 |
| --- | --- | --- | --- |
| 同一个 Wi-Fi | 家里/公司网络内的设备 | 不用 | 绝大多数人 |
| 内网穿透 / WireGuard | 只有你自己的设备 | 不用 | 经常在外面用 |
| 公网 + 域名 + HTTPS | 全世界（靠密码拦） | 要 | 团队共用、有固定服务器 |

不管走哪条，**连进来的那台设备都是用「配对码」拿授权，不是把密码敲过去**。

---

## 〇、两个总开关：默认都关着

**先看这里。** 配对码生成不出来、手机上看不到终端里在跑的活儿，十有八九不是坏了，是开关没开。
这两个开关在管理后台 →「客户端安全」→「远程访问与远程操控」，**新装的机器上默认都是关的**——一台只有自己用的电脑不该
天生就能被远程连上，要用再开，这是刻意的。

| 开关 | 开了之后多出什么 | 关着的时候 |
| --- | --- | --- |
| **允许远程设备接入**（`remote_devices`） | 「设置 → 设备」里才生成得出配对码，手机 / 另一台电脑才扫得进来共用这份数据（密码不会离开这台机器） | 生成配对码直接被拒（`403`，界面上写明是开关关着，不是码错了）。**而且关掉的同一刻，已经扫码连上的设备下一次请求就被踢下线**——不用一台台去撤，也不用等令牌过期 |
| **允许远程操控终端任务**（`remote_control`） | 网页和手机上才看得见这台机器终端里 `openworkbuddy` 正在跑的活儿，才能给它插话、替它批准危险操作 | 终端照跑不误，只是外面看不见也插不上手（`/api/cli/*` 一律回空列表 + `remote_off`）。**这一条另外还要求你是这台机器的主人**——平台所有者之外的账号，开关开着也看不到 |

关掉 `remote_devices` 会踢设备这件事值得单独记一笔：它是**应急开关**。笔记本丢了、某台设备不知道
还在谁手上、临时要把所有外部入口一次性掐掉——拨这一下就够了，比一台台点「撤销」快，也不会漏。
重新打开之后，之前那些设备**不会自己回来**，得重新扫码——被踢掉的是令牌本身，不是暂时挂起。

## 一、配对码是怎么回事

跟电视上登录视频网站是一个套路：码在**已经登录的那台机器**上生成，到**新设备**上填。

在电脑上（二选一）：

- 终端里：`openworkbuddy pair`
- 网页里：设置 → 安全 → 远程访问 → 生成配对码

都会给你一串 8 位的码和一个二维码。手机扫码，或者打开那个地址点「用配对码连接」，
把码填进去就行。

**为什么不直接输密码。** 密码是「一把钥匙开所有门」：手机丢了，你得改密码，
于是所有设备一起被踢下线。配对出来的是一条**只属于那台设备**的凭证——
手机丢了就把那一台踢掉，别的设备照常用，密码一个字都不用改。

这串码的几条性质，是照着「它就是一把能直接开门的钥匙」来设计的：

- **三分钟作废**，且**只能用一次**（换令牌之前就先删掉，中间出错也不会留下一个还能再用的码）。
- **只存在服务进程的内存里**，重启就没了，硬盘上不留。
- 字符表抠掉了 `I L O 0 1`——这串是要人照着念、照着敲的，少一类看错就少一次白试。
- 撞码有闸：同一个 IP 试错 6 次就锁 15 分钟。8 位码 ≈ 40 bit，没有这道闸，
  慢慢撞总能撞上。
- 码发出去之后你才把某个账号停用了？**换令牌的那一刻还会再查一次**，
  停用了的换不出来。

### 已授权设备

设置 → 安全 → 远程访问 里列着所有还能进来的设备：叫什么、从哪个地址来、
上次什么时候活动、是不是你正在用的这一台。想断哪台点「踢掉」，**当场生效**，
不用等令牌自己过期。

那张表里的「设备 id」是令牌的哈希，不是令牌本身——就算这一页被人看见了，
他也拿不走任何一台设备的登录态。

## 二、同一个 Wi-Fi（推荐先试这个）

`openworkbuddy pair` 出的二维码里，地址就是这台电脑在局域网里的地址（`192.168.x.x` 这种）。
手机跟电脑连同一个 Wi-Fi，扫了就能用。

要让服务听局域网而不只是本机，在 `config.json` 里：

```json
{ "server": { "host": "0.0.0.0", "port": 3800 } }
```

**这一步的含义要想清楚**：改完之后，**同一个网络里的任何设备**都能访问到这个端口。
家里的 Wi-Fi 一般没问题；咖啡馆、酒店、公司访客网络就别开了——
那种网络里「同一个局域网」可能意味着一屋子陌生人。

局域网里是明文 HTTP。同网段的人在技术上能看到内容。家里自用可以接受，
别的场合请往下看。

## 三、经常在外面用：内网穿透 / WireGuard

想在外面（4G、别人家的网）也能用，又不想把服务挂到公网上，
就用一条**只有你自己的设备能进**的隧道：

- **WireGuard / Tailscale 一类的组网**：手机装个客户端，连上之后就像回到家里的网，
  地址还是那个 `192.168.x.x`。服务本身完全不用暴露到公网。**这是隐私上最干净的一条**。
- **frp / ngrok 一类的穿透**：简单，但流量要过第三方的服务器。
  那台服务器在技术上能看到内容——除非你自己搭 frps。

## 四、挂到公网上：必须先做的几件事

如果你确实要给一个域名、让团队从外面用，那它就是一个**公网服务**了，
下面几条不是建议，是底线：

1. **一定要 HTTPS。** 没有 TLS 的话，密码、配对码、你所有的对话内容，
   在路上任何一跳都是明文。
2. **别开自助注册。** 设置里的「开放注册」默认是关的，保持关着，用邀请码加人。
3. **前面挂一层 nginx。** 模板是 `deploy/nginx.conf`（用 caddy 的话是 `deploy/Caddyfile`，
   两个都带好了下面这些设置，选一个就行）。
4. **备份 `users.json`。** 它是账号和令牌的唯一一份底账。

### 隐私边界：说实话的部分

**只要你在中间放了一台反向代理（nginx），TLS 就在它那里终止，
那台机器在技术上就能看到明文。** 这跟软件本身开不开源没关系——
它是「反向代理」这个结构决定的。

所以：

- 服务器是你自己的 → 能看到明文的只有你自己。**没问题。**
- 服务器是租的 VPS → 云厂商在物理上有能力接触到那台机器。
  威胁模型里如果包含「不信任云厂商」，那这条路就不成立。
- 真要做到端到端 → 得让 TLS **一路到应用**（nginx 用 TCP 层 `stream` 透传，
  不解密），或者干脆别走公网，回到第三节的 WireGuard。

模型那一头是另一件事：**你配的是哪家的模型，对话内容就会发到哪家去。**
想连这一段也留在本地，用 设置 → 引擎 里的本机引擎（Ollama 一类）。

## 五、慢的话看这里

网页第一次打开要拉的东西已经压过一轮了（实测 1134 KB → 388 KB，省 66%；
画布那 144 KB 是用到才加载，不进首屏）。
如果挂了 nginx 还是觉得卡，多半卡在**每次请求都重新握一次手**上。
`deploy/nginx.conf` 里已经带好了这几条，自己改的话别漏：

```nginx
# 1. HTTP/2：一条连接跑完所有请求，不用为每个文件各握一次手
listen 443 ssl;
http2 on;

# 2. TLS 会话复用：第二次连上来不用重新算一遍密钥（省 0.3~1.3 秒）
ssl_session_cache   shared:SSL:10m;
ssl_session_timeout 1d;
ssl_session_tickets on;

# 3. 到后端也保持长连接，别一个请求一条 TCP
location / {
    proxy_pass http://127.0.0.1:3800;
    proxy_http_version 1.1;
    proxy_set_header Connection "";     # 默认会发 close，这行是关键

    # 4. 流式回答不能被缓冲，否则「一个字一个字出」会变成「卡住然后哗一下全出来」
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

> 第 4 条尤其容易踩。网上常见的说法是「nginx 这层别开 gzip，会毁掉 SSE」——
> 这话只对了一半，而差的那一半才是真的判据。实测（nginx 1.30.0，上游每 250ms 吐一行，
> 量每行到达客户端的时刻）：
>
> | nginx 设置 | 每行到达时刻 |
> |---|---|
> | `gzip off` + `proxy_buffering off` | 276 / 523 / 774 / 1025 / 1276 / 1527ms —— 逐行到 |
> | `gzip on`（`gzip_types` 不含 SSE 类型）+ `proxy_buffering off` | 256 / 523 / 758 / 1009 / 1260 / 1515ms —— 逐行到 |
> | `gzip on`（`gzip_types` 不含 SSE 类型）+ `proxy_buffering on` | 272 / 522 / 773 / 1023 / 1274 / 1526ms —— 逐行到 |
> | `gzip on`（`gzip_types` **含** `text/event-stream`）+ `proxy_buffering off` | 273 / 510 / 761 / 1012 / 1263 / 1515ms —— 逐行到 |
> | `gzip on`（`gzip_types` **含** `text/event-stream`）+ `proxy_buffering on` | **1511ms × 6 —— 全卡到最后一起出** |
>
> 结论：要出事得**同时**满足两条 —— gzip 真的压到了 `text/event-stream`，**并且**开着缓冲。
> 少任何一条都还能逐行流。而 nginx 自带的 `gzip_types` 默认只有 `text/html`，
> 压不到 SSE；真正的雷是从网上抄一长串带 `text/event-stream` 的 MIME 清单，
> 或者图省事写 `gzip_types *;`。
>
> 所以 `deploy/nginx.conf` 是**开着 gzip** 的，只是把清单钉死、并且同时关掉缓冲（两道保险）。
> 开着的理由：应用自己压的只有两样 —— 磁盘上的静态文件（`static-compress.js`）和
> `res.json` 出去的动态 JSON（`json-compress.js`）。漏网的那些正好都不小，
> 只有 nginx 这层够得着：`/metrics` 的纯文本、审计日志导出、以及工作区里
> `res.download` / `res.sendFile` 直接发的成果文件（`.md` / `.csv` / `.txt` / `.svg`）。
> 也不会被压两遍——上游带着 `Content-Encoding` 上来时 nginx 直接放行
> （实测 656 字节进、656 字节出）。老版本（还没有这两层中间件的）挂上来也能直接受益。
>
> 另外别写 `proxy_set_header Accept-Encoding "";`（网上模板很爱加），
> 那会让应用只能发未压缩的原文，首屏从 388 KB 变回 1134 KB。
>
> caddy 那条路不用操这个心：实测 v2.11.4 的 `encode` 本来就跳过 `text/event-stream`，
> 写不写 `flush_interval -1` 都是逐行到（模板里仍然留着，当第二道保险）。
