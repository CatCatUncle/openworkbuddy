# Agent 执行架构与进度核对

本文对应开发中的源码改动，尚未随 v0.18.2 安装包发布。

## 当前执行方式

内置引擎使用模型与工具交替执行的循环：模型观察已有结果，决定下一批工具，运行时执行并把结果交回模型。它接近 ReAct / tool-calling 模式，配有进度清单、专家委派、上下文压缩、权限检查、执行上限、恢复与成果核验。

工具并非全部串行。同一轮中连续的只读工具可以并行，独立的媒体生成工具也有单独的并发上限。写文件、命令和专家委派仍保持模型给出的顺序，避免改乱依赖。同一轮的批次并行还不构成跨轮的 DAG 调度器。

界面的 Plan 模式是只读规划权限：可以读、查、分析，不能修改文件。它不等于把内置运行时切换成独立的 Planner / Executor 两套代理。本机 Claude Code、Codex 模式则由各自 CLI 管理模型循环，OpenWorkBuddy 负责接入和事件展示。

## 三种方式有什么区别

| 方式 | 怎样推进 | 适合的任务 | 需要付出的代价 |
| --- | --- | --- | --- |
| 当前工具循环 | 观察结果，再决定下一步；清单辅助跟踪 | 边做边观察的办公、文件编辑、视频调整 | 清单需要和执行状态对齐，不能只依赖开场计划 |
| Plan / Execute | 明确规划，再交执行器执行；必要时重新规划 | 可拆成阶段、有明确交付标准的长任务 | 需要维护计划、执行结果与重规划规则；此模式本身并不排斥并行 |
| LLMCompiler | 规划器输出含依赖和变量的任务图，调度器执行已就绪节点，再判断完成或重规划 | 多来源调研、批量独立生成等有并行空间的任务 | 需要可靠的依赖解析、资源冲突管理、失败处理和结果汇合 |

DAG 是有向无环依赖图。做一份报告时，“读取模板”“查政策”“整理销售数据”可以同时做；“汇总报告”要等前三项结束。若任务都是依次修改同一个文件，或者渲染必须等剪辑完成，换成 DAG 也不能消除这些依赖。

LLMCompiler 是专门处理任务依赖与并行函数调用的方案，仍有适用场景。选择它要看任务依赖和测量结果，不能把这些架构看成必须逐级升级的版本号。原论文的提速结果来自特定基准，不能直接套用到实际办公或视频任务。

参考：[LLMCompiler 论文](https://arxiv.org/abs/2312.04511)、[原始实现](https://github.com/SqueezeAILab/LLMCompiler)、[LangChain 对规划型代理的说明](https://www.langchain.com/blog/planning-agents)。

## 这次优先补什么

针对“工具已经执行很多次，清单仍停在 0/6”的问题，先补运行时的进度核对，而非替换整个引擎。

- 已有未完成清单时，执行 6 个工具，或清单确认超过 90 秒且至少有一个工具返回，下次模型调用要求核对清单。提示放在系统提示的易变尾部，不改变稳定前缀缓存，不另调一个判断模型。
- 模型忽略一次提醒、下一轮仍未核对时，内置引擎暂缓新的写入、命令、生成与委派；读取、查询、加载技能、征询用户、查看及停止后台命令仍可使用。成功调用 `todo_write` 核对后即可恢复，仍在进行的条目可以保持原状态。
- 文件型 `PROGRESS.md` 也参与中途核对提醒，实际写入后立即发布更新。此路径通过文件更新同步，不强制改为 `todo_write`，也不施加清单型暂缓规则。只读取本任务目录的进度档，其他任务同名文件不会覆盖当前计划。
- 一个工具正在运行时不额外发起模型核对，也不打断长时间渲染；核对发生在工具返回后的模型轮次。原有手动停止、超时和执行上限继续生效。
- 只有成功的清单更新才刷新确认时间；工具调用次数与运行时长不换算成完成率。确认属于模型根据工具结果作出的报告，不代表新增了一套自动验收器。
- 手动说“继续”“继续完成”“继续给我完成”时，在尚未被压缩丢弃的工具历史中恢复最近成功的未完成清单。恢复记录注明来自上一轮、时间未知，须先核对现场；新任务不继承旧清单。
- 界面区分“已确认完成数 / 清单当前项”和“此刻执行的操作”，过期清单提示“待核对”。待做条目显示“下一项”，专家进度不能覆盖主任务，空清单撤下，历史回放不编造确认时间，结束后迟到的清单不覆盖结果。
- 清单仍未完成、收尾核验次数用尽时，明确记录为未完成。阻塞事项保留未完成状态，不要求把它勾成已完成。

核对阈值决定提醒时机，不代表某项任务应当在 6 次调用或 90 秒内做完。模型不遵循核对要求时可能需要额外一轮调用，仍受现有步数与时间上限约束。

这套执行约束适用于内置引擎。Codex 的清单事件补充真实事件时间并复用相同展示规则；外部 CLI 的执行循环不受内置引擎的进度闸门控制。

相关实现：`src/agent/progress.js`、`src/agent/agent.js`、`public/js/app-01.js`。测试覆盖工具实际执行、暂缓与恢复、长工具、手动续做、历史与子任务隔离。

## 之后什么时候考虑 DAG

先测量任务在模型等待、独立工具等待、写文件和渲染上各花多少时间。若独立网络查询或批量生成占主要耗时，再为这些场景增加显式依赖调度，保留文件写入顺序和现有审批。需要评估总耗时、费用、失败率、取消与重试行为，不能只看并发数量。

执行管理层还应持续关注上下文、持久状态、恢复与验收。这些问题同样存在于 Plan / Execute 或 DAG 内部。参考：[Deep Agents 官方概述](https://docs.langchain.com/oss/javascript/deepagents/overview)、[Anthropic 的长任务执行管理](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。
